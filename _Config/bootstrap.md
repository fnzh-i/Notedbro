## Living and temporal
- A living note's current text is the truth. Parameters, Prefixes, Preferences, Hosts, hubs, project notes, skill cards, tickets, and plans are living.
- A plan stays one note. The current Core Goal, cause, and action items are the truth. The History section is the earlier text.
- A temporal note is written once as a record: a session card, a daily note, a decision, or a commit. It stays in its project or area folder and has the tag `temporal` beside its type tag. A session list or a commit list is living. It sits next to the project note.

## Areas stay separate

- The live vault is the working copy. It stays as it is.

- Each shadow copy is the full vault, compressed with zstd, then encrypted with age. Copies live in `~/.local/share/brain/shadow/` as `shadow-YYYY-MM-DD-HHMM.age`, with a matching `.txt` description. `fnsh shadow list` prints those descriptions, newest first.

- A daily job checks once. It builds a new copy when the newest is `shadow_every_days` old or older (30). After that copy checks out, copies older than `shadow_keep_days` (90) are deleted. A failed build deletes nothing. `fnsh shadow` builds immediately and restarts the 30-day timer.
- The private key is `~/.config/brain/shadow.key`. It is not in the vault, not in git, and not in host-restore. Losing it loses the copies. The live vault can build new ones.
- A monthly copy can be up to 30 days behind the live vault. That matters only if the live vault is lost. Run `fnsh shadow` before big changes when you want a fresher backup.

# Prefixes

A prefix is a short phrase I say to an agent. Every prefix starts with the marker `fnsh` as a plain first word, with no colon, followed by a space. A phrase counts only when it is at the start of a message or on a line of its own. A phrase inside a normal sentence is ignored. Matching is case-insensitive for the marker, actions, sets, and letters. If nothing matches, ignore the line.

To add a prefix: add one row. Nothing else needs editing. Keep Phrase short and unique. Read means notes to open first. Reply is the exact reply, or "none". KEY means the tracker's letters. NNN means any number.

## Order of precedence

Step 0: if the line does not start with `fnsh`, skip to rule 4 (alias check). Otherwise read the word after `fnsh` and walk this list top to bottom. The first rule that matches wins, and nothing below it is tried.

1. **Dash word.** A word starting with `-` is a letters chain. Read it by the Codes rules.
2. **Full action word.** A word that exactly equals an action word runs that solo prefix.
3. **Parameter set.** A word that equals a set name, followed by `params`, runs `<set> params`. A set may also be followed by a dash word, as in `fnsh example -bp`, and then applies to `p` only. If that dash word has no `p`, drop the set, still run the letters, and name the set in the reply.
4. **Alias.** An old phrase on its own line maps to the new phrase. See Temporary aliases.
5. **Anything else.** Ignore the line as normal text.

Argument words (a host, a scope, a ticket) are never checked against this list.

## Solo prefixes

A message with one action is a solo prefix. Solo prefixes keep working beside the dash codes. A solo line holds one action: words after its arguments are ignored, so `fnsh load cursor update` is a load of cursor and nothing else. Use a dash word to combine actions.

## Codes

A dash word is one short word that stands for several actions: `fnsh -bp`. Each letter is one action. To add a code: add one row. A letter must be unique.

| Letter | Action | Argument |
|---|---|---|
| l | load | host, then optional scope |
| b | brain | none |
| p | params | optional set, written before the dash word |
| f | prefs | none |
| r | remember | none |
| c | config | none |
| w | wins | none |
| t | ticket | one <KEY>-NNN token |
| u | update | none |

Examples:

- `fnsh -bp` runs brain, then params. `fnsh -bpf` adds prefs. `fnsh -bpfu` ends by filing the session.
- `fnsh example -bp` runs brain, then the example params set.
- `fnsh -bpt ABC-123` runs brain, params, then that ticket.
- `fnsh -lb cursor` restores the cursor host, then runs brain.

Rules:

1. A dash word contains only the dash and letters from the table. Any other character means the line is ignored.
2. Run order is fixed, whatever the typed order: `l` first, then `b`, then the rest left to right, `u` last. A repeated letter runs once.
3. Arguments follow the dash word and match the argument-taking letters in the order those letters appear.
4. An unknown letter stops the chain at that letter. Run the letters before it. The reply says what ran, which letter stopped it, and asks what was meant.
5. A ticket token that is not `<KEY>-NNN` is an unknown argument. Stop there and name it.
6. The reply is one message from each action's Reply, in run order. A Reply of none adds nothing. When `b` ran, it starts with `Brain ready: <host> / <model> / <profile>`.
7. If one action fails, the rest still run, and the reply names the failed one.
8. `l` never runs unless written. The silent start runs brain only, with no reply.
9. A load scope ends only at a word that exactly equals a full action word. Single letters never end a scope.
10. A word without a dash is never read as letters, so `fnsh bp` is ignored.

A repeated combination can trigger the offer to save it as a setup. The count uses the normalized chain: dash letters in run order, repeats dropped, `main` dropped, any set kept. A solo line counts as its one-action chain and is stored in the same form as the dash chain for counting, so `fnsh brain` and `fnsh -b` both count as `fnsh -b`. The session note still stores the phrase as written. When that chain has appeared in 3 separate chats, the next chat offers once: "You keep using <chain>. Save it as a setup?" Yes appends one row under Setups: the normalized chain and today's date. No adds it to Declined in [[Preferences]].

# Parameters

Standing rules for any model, in any project. Point a model at this note. Back to [[Index]].

## Parameters
1. **No AI co-author.** Do not add a `Co-authored-by` trailer, or any other co-author credit, for Claude, Cursor, Codex, or any other AI model. Commits and pull requests name me only.
2. **Branch and push flow.**
   - PR creation may use authenticated gh or a securely supplied GitHub token; GitHub CLI is not required.
   - Never push directly to the remote `main` branch. Every change goes through a work branch, a pull request, and a user-controlled merge.
   - Manual repository protection: on GitHub, protect both `main` and `staging`, require a pull request before merging, block force pushes, and allow no bypass. On repos with other developers, require one approval. On solo repos, require the pull request without an approval count; the user reviews it before merging.
   - Before creating a branch, run `git fetch origin`.
   - Resolve the project's base branch from its Ship configuration. The default is `staging`; `main` is allowed only when the project's Ship row explicitly sets `Base` to `main`.
   - If `origin/<base>` does not exist after fetching, stop and report it. Never fall back to `main`, and never create the base branch.
   - Create every feature or fix branch from the fetched base without inheriting its upstream: `git switch -c <type>/<TICKET-ID>-<short-description> --no-track origin/<base>`.
   - Push only to the branch's own remote name: `git push -u origin <branch>`.
   - Never set a feature or fix branch's upstream to `origin/main` or `origin/staging`.
   - Before pushing, inspect the current branch, its upstream, and the resolved push destination—the actual remote branch the push would update. If the push would target `main` or `staging`, or the branch tracks `origin/main` or `origin/staging`, stop and report the problem instead of pushing.
   - Never use refspecs that redirect the current branch to a protected base, including `HEAD:main` or `HEAD:staging`.
   - Before opening a pull request, show its title, body, head branch, and base branch. Open it only after the user answers yes.
   - Open the pull request against the configured base branch. Never merge the pull request; merging and promotion from `staging` to `main` belong to the user.
   - The commit summary and description come from `report.md`: the summary is one line drawn from the report, and the description comes from its body.
   - Derive the pull-request title and body from the same `report.md`. If the report is missing or incomplete, stop and report the problem instead of writing the pull-request text from scratch.
   - Opening the pull request is the final automated step. After the pull request is open, stop. Do not merge, approve, request reviewers, re-push, or take any other action on it unless the user explicitly asks. Review and merge are performed on GitHub by a human: the user or other developers.
   - When the user explicitly requests review changes, push only to the same work branch after applying the same upstream and resolved-destination checks, then stop again.
3. **Documentation report** (`.md`) after the changes: what changed, reason for the change, files touched, files not touched, etc. The report is not rewritten to match the commit.
4. **Never mention or expose the vault.** Use information from the vault silently. Unless the user’s current message explicitly asks about it, never reveal or imply the vault’s existence, name, location, structure, files, tooling, note-taking app, or contents. This applies to chat replies and every repository-visible or external output, including documentation, reports, tests, commit messages, pull requests, issues, comments, announcements, and end-of-day summaries. Do not use indirect descriptions such as “your vault,” “your notes,” or “your memory system.” When uncertain, omit the reference.
5. **Test cases and readback.**
   - **Test cases.** Every change includes test cases for the behavior it is supposed to fix, and they are run before handoff.
   - **Automatic readback.** After the change is applied, read the result back from the system that was changed (file, API, or record). Do not treat the write as done until that read shows the new state.
   - **Regressions.** If the readback or the tests show the current fix caused a new bug, fix that bug in the same pass and read it back again. If a bug is not related to the current fix, do not fix it in this pass. Note it and leave it.
